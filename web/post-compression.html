From PyTorch to a 1.2 MB ONNX file

In short
  • Put the normalisation inside the exported graph: the runtime sends raw values and gets raw quantiles back. No second implementation to keep in sync.
  • Export with torch.onnx.export(..., dynamo=False) and the MHA fast path disabled; rewrite ops that have no ONNX translation.
  • Test parity with a tolerance relative to the series' scale, on nasty inputs (scales from 0.001 to 50,000, gaps, short series).
  • onnxruntime.quantization.quantize_dynamic, per-channel, first layer kept in float32: 3.6 MB → 1.2 MB. Then re-run the benchmark: it cost 0% on electricity, 1.5% on the shapes.

1. Put the scaler inside the model

Forecasting models normalise each input window (here: median, mean absolute deviation, then asinh) and un-normalise the output. If that code lives outside the model, you must re-implement it in every runtime: Python for training, JavaScript for the browser. The two versions will drift. Make it part of the module's forward, so it is exported with the weights:

The masked median is computed by sorting with missing values pushed to +∞. It is slow on paper and irrelevant in practice: the context is 512 values.

2. Export: two calls that fail and how to fix them

nn.TransformerEncoder's fused fast path has no ONNX translation. In eval mode PyTorch routes attention through a fused kernel, and export fails. Turn it off around the export with torch.backends.mha.set_fastpath_enabled(False).

torch.asinh did not export either. Rewrite it with basic ops, carefully. The textbook formula \(\log(z + \sqrt{z^2 + 1})\) subtracts two nearly equal numbers for large negative \(z\) and loses all precision. Use the symmetric form, and test it against torch.asinh (tests/test_losses.py):

Also: declare the batch dimension dynamic, use opset 17 or later, and name the input and output. Those names (context, quantiles) are what the browser code uses.

3. Parity: is the export faithful?

Run PyTorch and ONNX Runtime on the same inputs and compare. Two traps:

  • Absolute tolerances do not work. float32 keeps about 7 significant digits. On electricity around 50,000 MW, one rounding step is about 0.004, so atol=1e-4 fails on a correct export. Divide the error by the series' scale. sinh amplifies rounding in the far tails, so divide by the distance from the centre as well.
  • Easy inputs prove nothing. Test the paths the scaler takes: tiny and huge scales, offsets, missing gaps, left-padded short series.

Our export script fails if the fp32 maximum relative error exceeds 10⁻⁴. For the published student, the 99th-percentile relative error is 1.4 × 10⁻⁶ in fp32 and 5.0% in int8, over 1,000 stress windows (results/export/c1x_kd5m_3m.json).

4. int8: smaller, and almost as accurate

The first layer sees the scaled input directly; its errors propagate through everything after it. Per-channel scales stop one large weight from coarsening the rounding of a whole matrix. We also tried keeping the output head in fp32: no effect, because the dynamic quantiser does not quantise the Gemm node the head exports to. Check which nodes are actually quantised before you reason about them.

Parity error is not accuracy loss A 5% p99 output difference sounds bad. Re-scored on the benchmarks, the int8 student is indistinguishable from fp32 on fresh electricity (ratio 0.997 [0.996, 0.999]) and 1.5% worse on the shapes (1.015 [1.007, 1.022], results/site_pairs.json). Always re-run the metric you care about.

Checklist

  • Normalisation and de-normalisation inside forward.
  • dynamo=False, MHA fast path off, opset ≥ 17, dynamic batch, named input and output.
  • Rewrite unsupported ops in a numerically stable form; unit-test them against PyTorch.
  • Parity on stress inputs, tolerance relative to scale; fail the export script if it breaks.
  • quantize_dynamic, per-channel, first layer in fp32; list the nodes actually quantised.
  • Re-score the int8 model on your benchmarks.
