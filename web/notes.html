1 · Forecasting with quantiles

A point forecast says "tomorrow at noon: 52 GW". A probabilistic forecast says "50% chance below 52 GW, 90% chance below 55 GW…". Every model here outputs this as quantiles: 13 values at levels τ = 0.01, 0.05, 0.1, …, 0.9, 0.95, 0.99 for each of the 64 future steps.

How do you train a network to output the 0.9-quantile? With the pinball loss ρτ(y, q) = τ·(y − q) if y ≥ q, else (1 − τ)·(q − y). Under-predicting costs τ per unit, over-predicting costs 1 − τ. At τ = 0.9 under-prediction is 9× more expensive, so the best constant answer sits high: exactly at the 90th percentile of the data.

Switch the observations to "a teacher's quantiles". The minimum lands on the teacher's τ-quantile. Remember this; it is the whole trick of section 6.

2 · Scoring: WQL and its hidden bias

To score a forecast we average 2·ρτ over levels and time and divide by Σ|y| (so a 50 GW national series and a 3 GW region are comparable). That is the weighted quantile loss (WQL), and benchmarks like GIFT-Eval report it as "CRPS", the continuous ranked probability score, because CRPS = 2∫ρτ dτ and averaging over levels approximates that integral.

We wrote a test to check that approximation against the exact CRPS of a Gaussian forecast. It failed, and the failure was informative:

At the true quantile, the expected pinball loss is σ·φ(zτ): largest at the median, tiny in the tails. Dropping the tails (9 levels) removes small terms, so the average comes out too high. Our 13-level grid has extra tail levels with equal weight, so it comes out too low. Weighting each level by the probability mass it represents fixes both.

What we do with it: rankings use GIFT-Eval's 9-level WQL (the same bias for every model, and Toto 2.0 only outputs those 9 levels). The student's training loss uses mass weights, so it does not over-invest in the 1% and 99% tails.

3 · Fresh data and honest error bars

Foundation models are trained on huge scraped corpora. If a benchmark's test data is in there, the model is reciting, not forecasting. So our headline test set is French electricity consumption (RTE éCO2mix) published after every model was released. A unit test (tests/test_leakage.py) fails the build if any cutoff is violated.

The catch: "after the latest release" leaves only a few weeks of data, i.e. a few hundred windows from 13 series. Our first error bars treated each window as independent. They are not: windows from the same region share a regime, and with daily origins and a 64-hour horizon consecutive targets overlap. We switched to a cluster bootstrap: resample whole series, recompute the score, repeat 2000 times.

4 · The teacher zoo: what we learned reading the code

Before writing any adapter we read each package's source. Guessing would have been wrong several times:

  • Toto 2.0 is not toto-ts (that is Toto 1.0). The right package is toto-2, Python ≥ 3.12 only, which moved the whole project to 3.12.
  • Toto 2.0 outputs 9 fixed quantiles (0.1–0.9), no samples. Its head ignores requested levels. We extend to 1%/99% with the same exponential-tail rule t0 uses, and flag it.
  • t0 is not gated on Hugging Face, and t0-gamma natively emits all 13 of our levels.
  • Chronos-2 silently clamps levels outside its trained range (a log warning only), and its raw quantiles cross occasionally. We sort them (it never increases the loss) and record the rate.
  • Timestral's licence withdraws every right if your company's or employer's monthly revenue exceeds $20M, evaluation included. It stayed disabled until the owner confirmed this is a personal project (2026-11-13); it is now a comparator. Its forecast() turns two post-processing tricks on by default; we turn them off, as for t0.

5 · Anatomy of the student

The student is small on purpose (~1M parameters, ? MB in fp32), so it can run on every keystroke in a browser. Four pieces:

a) A scaler that lives inside the model

A drawing has no units, and a region's consumption is in MW. Before the network sees anything we subtract a location and divide by a scale computed from the context only (never the future, which would leak). We use the median and the mean absolute deviation from it, not the mean and standard deviation, because one spike can drag a mean and blow up a standard deviation. Then asinh squashes large excursions while staying almost linear near zero.

b) Patches

512 steps become 32 patches of 16. Each patch is embedded together with a 16-bit "observed" mask, so a missing value is not confused with a zero.

c) A transformer encoder

4 layers, width 128, 4 heads. A learned "forecast token" attends to all patches; its final state feeds the head.

d) A head whose quantiles cannot cross

The head predicts the median plus 12 numbers turned positive by softplus; each further level is the previous one plus a gap. Teachers had to sort their outputs (Toto) or occasionally failed to (Chronos-2). Ours is monotone by construction.

6 · Distilling a probabilistic model

Classic distillation (Hinton et al.) matches a student's softened class probabilities to a teacher's with a KL divergence. A quantile forecaster has no classes and no logits, so there is nothing to soften. What the teacher does give us is its predictive distribution, seen through its quantiles. Three ways to use it:

  • Lgt: pinball against the true future only. This is the "floor" every distilled student must beat.
  • Lkd, huber: regress each student quantile onto the teacher's quantile at the same level. Simple, but it treats levels independently and copies the teacher's errors with full weight.
  • Lkd, pinball: treat the teacher's quantiles as weighted pseudo-observations and apply the pinball loss. That is the widget in section 1 with "teacher" selected: the minimum is the teacher's own quantile, so this matches the teacher's distribution, not just 13 numbers.

Training mixes them: L = (1 − α)·Lgt + α·Lkd. α = 0 is pure ground truth, α = 1 pure imitation.

The plan called for a "sample-pinball" loss on Toto's Monte-Carlo samples. Reading Toto 2.0's code showed it produces no samples. Lkd, pinball with mass weights is the same loss with the teacher's quantiles in place of samples, so nothing was lost. A unit test confirms that optimising it recovers the teacher's quantiles.

All losses are computed in the student's scaled space. That is legal for quantiles: they commute with monotone transforms (the 0.9-quantile of asinh(Y) is asinh of the 0.9-quantile of Y), so the minimiser does not move.

No distillation results yet. The code is tested, but no KD run beyond a 300-step pipeline check has been run. That is the next phase, to design together.

7 · Shipping it to the browser

The student is exported to ONNX with the scaler inside the graph: the page sends raw numbers (NaN for missing) and receives raw-space quantiles. There is no JavaScript re-implementation of the normalisation to drift out of sync.

  • Pitfall 1: PyTorch's TorchScript exporter has no ONNX translation for asinh. We wrote it from basic ops, sign(z)·log(|z| + √(z²+1)); using |z| avoids catastrophic cancellation for large negative z.
  • Pitfall 2: "max abs diff < 1e-4" is impossible in float32 on 50,000 MW data, and sinh amplifies rounding in deep tails. The parity check uses error / max(scale, |q − loc|).
