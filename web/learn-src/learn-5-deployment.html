In one minute
  • Small models are cheap to run: our student forecasts in about 2 milliseconds in a browser tab.
  • To leave Python, the model is exported as an ONNX file, a portable recipe any runtime can execute. We put the pre-processing inside it.
  • int8 quantisation rounds weights to 8-bit integers: 4× smaller, almost the same accuracy if a few sensitive layers stay in full precision.
  • Always check the exported model gives the same answers as the original (a parity test).

Size, latency, accuracy

Parameters set the file size and roughly the compute per forecast. Latency also depends on the number of tokens (sequence length), the batch size and the runtime. For an interactive demo that forecasts on every pen move, the budget is a few milliseconds and a few megabytes.

Note the shape of the table: going from 4M to 300M parameters multiplies latency by about 25 and improves the relative score by roughly 15% on the shapes. Distillation tries to keep most of that gain at the small end.

Exporting the model: ONNX

Intuition PyTorch is a Python program; a browser cannot run it. ONNX is a file describing the computation as a graph of standard operations (MatMul, Add, Softmax…) plus the weights. Any ONNX runtime (Python, C++, the browser) executes the same graph.
Analogy ONNX is to a model what PDF is to a document: you write it in one tool, and anyone can open it anywhere without that tool. Putting the scaler inside is like embedding the fonts in the PDF.

The most important design choice: put the preprocessing inside the graph. Our scaler (median, MAD, asinh) and the un-scaling are part of the exported model. The browser sends raw numbers with NaN for missing values and gets raw-space quantiles back. There is no second implementation of the normalisation in JavaScript that could drift out of sync.

Pitfall: not every operation exports PyTorch's exporter had no ONNX translation for torch.asinh. We rewrote it with basic operations. The naive formula log(z + √(z² + 1)) loses all precision for large negative z (catastrophic cancellation: two nearly equal numbers subtracted), so we use the symmetric form sign(z) · log(|z| + √(z² + 1)) and a unit test against torch.asinh.

Parity: is the export faithful?

A parity test runs the PyTorch model and the ONNX file on the same inputs and compares. The tolerance must match the number format: float32 keeps about 7 significant digits, so on electricity data around 50,000 MW an absolute tolerance of 0.0001 is impossible (one rounding step is about 0.004). We use an error relative to the series' scale and to the value's distance from the centre. The test inputs are deliberately nasty: scales from 0.001 to 50,000, gaps, very short series.

int8 quantisation

Intuition Store each weight as an 8-bit integer instead of a 32-bit float, plus one scale factor per group of weights. Four times smaller, and integer arithmetic can be faster. The price: each weight is rounded to the nearest of 255 levels.
Analogy Rounding prices to the nearest euro is fine for a supermarket receipt, and a disaster if one item costs 10,000 € and the rest cost cents: with one shared rounding step, all the small prices become 0. Per-channel scales give each shelf its own price tag precision.
Formally (symmetric int8) $$s = \frac{\max \lvert w\rvert}{127}, \qquad q = \operatorname{round}\!\left(\frac{w}{s}\right) \in [-127, 127], \qquad \hat{w} = s \cdot q$$

The rounding error per weight is at most s / 2. One large weight makes s large, and then every small weight of the group is rounded coarsely.

Increase the outlier in channel 0 with one shared scale: every channel loses precision. Tick "one scale per channel": only channel 0 suffers.

  • Per-channel scales isolate outliers (the widget).
  • Dynamic quantisation stores weights in int8 and computes activation scales on the fly: no calibration data needed. Static quantisation fixes activation scales from a calibration set: faster, more work.
  • Not every layer is equally sensitive. In our student, keeping the patch embedding (the first layer, which sees the raw-scale input) in float32 roughly halved the int8 error.
In this project int8 changes outputs by about 3% (99th percentile, stress-test inputs), yet the relative WQL on both test sets is unchanged to three decimals. Parity error and accuracy loss are different things: always measure the metric you care about.

Running it in the browser

  • onnxruntime-web executes the ONNX graph with WebAssembly (CPU) or WebGPU. Our 1M-parameter student takes about 2 ms per forecast in onnxruntime-web's WASM runtime on one thread (measured under Node.js; in-browser timing is shown live in Draw mode).
  • Threads in WASM need the page to be "cross-origin isolated" (special HTTP headers). Static hosts like GitHub Pages do not send them, so the demo runs single-threaded and says so.
  • Measure honestly: time only session.run, after a warm-up, and report a median over many runs. The first call includes compilation and is much slower.
  • Ship small files: the fp32 model is about 4 MB, the int8 one about 1.3 MB. The runtime itself is the largest download (the WASM binary, about 15 MB before compression).

Check yourself

1. Why include the scaler in the ONNX graph instead of re-implementing it in JavaScript?

One implementation means it cannot drift: the parity test covers preprocessing and network together, and the browser cannot normalise differently from training.

2. A weight matrix has one weight 30× larger than the others. Per-tensor int8: what happens to the small weights?

The scale is set by the large weight, so the small weights fall on only a few of the 255 levels (many round to 0). Per-channel scales or keeping that layer in float32 avoid it.

3. The ONNX output differs from PyTorch by 0.004 on a value of 52,000. Bug?

Probably not: that is about one float32 rounding step at that magnitude (relative 8 × 10⁻⁸). Judge parity relative to the values' scale.

4. The first forecast in the browser takes 300 ms, the next ones 2 ms. Which number goes in the paper?

Report both, labelled: the steady-state median after warm-up (2 ms) as latency, and the first-call time as "cold start".
